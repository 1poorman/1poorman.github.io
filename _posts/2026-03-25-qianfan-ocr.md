> 本文从**技术原理、主流方案选型、部署实践**三个层面，记录千帆 OCR 的试用结论，并与 MinerU、DeepSeek-OCR、PP-ChatOCRv4 做横向对比。

## 1. OCR 技术演进：从"识别文字"到"理解文档"

### 1.1 传统 OCR 的经典流水线

传统 OCR 通常拆成多个独立模块串行执行：

```
图像预处理 → 文本检测(Det) → 文本识别(Rec) → 后处理/结构化
```

| 阶段 | 代表方法 | 作用 |
| :--- | :--- | :--- |
| 文本检测 | DBNet/DBNet++、EAST | 定位文本行/词的包围框 |
| 文本识别 | CRNN(CTC)、SVTR、PP-OCRv4 | 将框内图像转为字符序列 |
| 版面分析 | PP-StructureV3、LayoutLM | 划分标题/正文/表格/图片区域 |
| 结构化 | 表格还原、公式识别 | 输出 Markdown / HTML |

这类方案的优点是**模块解耦、单模块轻量、可控性强**；缺点是**误差逐级累积**——检测漏框、识别错字都会向下传导，且复杂版式（公式、跨列表格、双栏）往往需要大量后处理规则。

### 1.2 端到端与多模态大模型路线

近几年出现两条新路线：

1. **端到端模型**：检测+识别一体化训练，共享视觉特征，减少中间误差。
2. **多模态大模型（VLM）**：以视觉编码器 + LLM 解码器直接"看图写字"，天然具备**上下文理解与实体抽取**能力，输出结构化的 Markdown / 实体列表。

> 核心变化：OCR 从"像素→字符"的感知问题，升级为"文档→结构化知识"的**理解问题**，这正好解释了为什么文档解析类产品都开始叠加 LLM 环节。

## 2. 四种方案的架构对比

| 方案 | 架构类型 | 开源 | 核心思路 | 强项 |
| :--- | :--- | :---: | :--- | :--- |
| **Qianfan-OCR** | 端到端 + 实体抽取 | 闭源/API | 识别与实体提取一体化，直接输出可查找实体 | 长文档、知识抽取 |
| **MinerU** | 模块化流水线 | ✅ | PDF-Extract-Kit，检测+版面+表格+公式 | 复杂版式还原、公式/表格 |
| **DeepSeek-OCR** | 多模态大模型 | ✅ | VLM 直接读图转 Markdown | 拍照/低质图、跨语种 |
| **PP-ChatOCRv4** | 模块化 + LLM | ✅ | PP-OCRv4 识别 + 版式 + 文心 LLM(ernie-3.5-8k) | 中文垂类、可控抽取 |

### 2.1 Qianfan-ocr：端到端模型

- 文本识别与实体提取一体化，支持**文档直接输出带索引的查找实体**；
- 适合把"扫描件 → 结构化知识库"一步到位，省去 OCR 之后再接 NER 的二次开发。

### 2.2 PP-ChatOCRv4：模块化

- **文本识别 + 版式识别 + 语言模型（ernie-3.5-8k）**三件套；
- 先由识别/版式模块产出结构化中间结果，再由文心 LLM 做语义理解与自由问答抽取，好处是**每个环节可替换、可调优**。

### 2.3 MinerU

- 开源文档解析工具，主攻 PDF；
- 擅长**表格结构还原、公式识别、双栏排版**，输出高质量 Markdown，常被用作 RAG 的数据预处理层。

### 2.4 DeepSeek-OCR

- 开源 VLM，对拍照文本、模糊/倾斜、手写等"非理想输入"鲁棒性好；
- 直接输出 Markdown，适合作为通用图文抽取底座。

## 3. Qianfan-OCR 实测要点

试用过程中的关键参数记录（按实际环境为准，不同版本/服务形态会有差异）：

- `max_tokens = 16M`：意味着可一次性吃下超长文档（整本书级别），无需频繁分块切窗，长程依赖的实体抽取质量更稳；
- **显存占用约 11G**：单卡（如 24G 消费级/专业卡）即可私有化部署，门槛不高。

**实测结论方向**（建议按自己数据集补全数据）：

| 维度 | Qianfan-OCR 表现 | 备注 |
| :--- | :--- | :--- |
| 长文档 | 依赖大上下文，分段一致性较好 | 16M tokens 上限 |
| 实体抽取 | 端到端一次到位 | 需与模块化 NER 对比精度 |
| 版式复杂表格 | 视版本而定 | MinerU 仍是强基线 |
| 部署成本 | ~11G 显存可跑 | 见第 4 节 |

## 4. 部署实践

### 4.1 三种部署形态

1. **在线 API**：调百度千帆平台接口，免运维，按量计费，适合快速验证与低频场景。
2. **私有化/本地部署**：拉取模型权重，用推理框架起服务，适合数据敏感、高频调用场景。
3. **边缘/离线**：量化压缩后部署到本地机器，用于内网无外网环境。

### 4.2 本地部署要点

- **显存规划**：实测约 11G，选用 16G/24G 显存卡即可，留出 KV cache 余量；
- **上下文与批处理**：长文档场景需关注 max_tokens 与首 token 延迟的平衡，可用连续批处理（Continuous Batching）提升吞吐；
- **量化可选**：对精度敏感优先 FP16/BF16；追求吞吐可尝试 FP8/INT4（注意长文档抽取精度回退风险）。

### 4.3 生产链路建议

```
PDF/扫描件/拍照图
      │
      ▼
OCR 解析层（Qianfan-OCR / MinerU / PP-ChatOCRv4）
      │  输出 Markdown + 实体
      ▼
清洗/分块 → 向量化入库
      │
      ▼
RAG / 知识库问答 / 文档搜索
```

> 建议：**感知强的任务（版式还原、表格公式）**选 MinerU / PP-ChatOCRv4 流水线；**理解强的任务（长文档实体抽取、知识结构化）**选 Qianfan-OCR / VLM 类端到端方案；复杂场景可两者串联做交叉校验。

## 5. 小结与选型建议

- 追求**可控、可解释、中文垂类** → PP-ChatOCRv4（模块化，环节可替换）；
- 追求**复杂版式还原质量** → MinerU；
- 追求**拍照/低质图通用识别** → DeepSeek-OCR；
- 追求**长文档 + 实体抽取一体化、部署省心** → Qianfan-OCR。

> 注：文中 `max_tokens=16M`、显存 11G 等为试用实测值，具体能力与配额请以官方最新文档为准。
